ТК-01. Уведомление менеджера о новой покупке

ПолеЗначение
IDTC-001
НазваниеУведомление менеджера в ВК после успешной оплаты
Связанные требованияSR-01, SR-02, SYS-15, SYS-16
Предусловия1. Школа зарегистрирована в PayLect
2. В личном кабинете указан номер телефона менеджера в ВК
3. WordPress-виджет настроен и вставлен на страницу курса
Шаги1. Студент открывает страницу курса
2. Нажимает «Оплатить»
3. Вводит ФИО и телефон
4. Вводит данные карты на странице Т-Банка
5. Подтверждает платёж
Ожидаемый результат1. Платёж успешно проведён
2. Студент получил подтверждение
3. Менеджер получил сообщение в ВК < 10 секунд
4. В сообщении указаны: ФИО студента, телефон, название курса, сумма
Пост-условияВ личном кабинете PayLect появилась запись о платеже со статусом succeeded
ОкружениеТестовый WordPress, тестовый аккаунт Т-Банка

ТК-02. Автоматический retry при отказе карты

ПолеЗначение
IDTC-002
НазваниеRetry-механизм при временном отказе карты
Связанные требованияSR-03, SYS-10, SYS-11, SYS-13
Предусловия1. Оформлена подписка на курс
2. У студента есть карта с лимитом, которого хватает только на 2-ю попытку
3. В настройках школы установлено 3 retry-попытки
Шаги1. Наступает дата планового списания
2. Система пытается списать → отказ (недостаточно средств)
3. Ожидание 1 час → вторая попытка → отказ
4. Ожидание 24 часа → третья попытка → успех
Ожидаемый результат1. После первого отказа система не отправляет уведомление менеджеру
2. После успешной попытки списание зафиксировано
3. Дальнейшие retry-попытки не выполняются
Пост-условияВ логах аудита зафиксированы все 3 попытки с status: failed → failed → succeeded
ОкружениеТестовая среда PayLect с симулятором Т-Банка

2. В логах зафиксирована отправка
Пост-условия—

ТК-05. Выгрузка платежей в 1С

ПолеЗначение
IDTC-005
НазваниеЭкспорт платежей из PayLect во внешнюю обработку 1С
Связанные требованияSR-06, SYS-08, SYS-09
Предусловия1. В 1С:Бухгалтерия установлена внешняя обработка PayLect.epf
2. В обработку введён валидный API-ключ
3. За период с 01.04.2026 по 30.04.2026 есть 3 успешных платежа
Шаги1. Бухгалтер открывает обработку в 1С
2. Выбирает период: 01.04.2026 – 30.04.2026
3. Нажимает «Выгрузить платежи»

2. Получен ответ с 3 платежами
3. В 1С созданы 3 документа «Поступление на расчётный счет»
4. Документы проведены без ошибок
Пост-условияПри повторной выгрузке за тот же период дубли не создаются
ОкружениеТестовая 1С:Бухгалтерия 8.3, тестовый API-ключ

ТК-06. Уведомление менеджера после 3 отказов

ПолеЗначение
IDTC-006
НазваниеОтправка уведомления менеджеру после трёх неуспешных списаний
Связанные требованияSR-07, SYS-12
Предусловия1. У студента активна подписка
2. На карте студента недостаточно средств
3. В настройках школы: 3 retry-попытки
Шаги1. Попытка №1 (списание в плановую дату) → отказ
2. Попытка №2 (через 1 час) → отказ
3. Попытка №3 (через 24 часа) → отказ
4. Попытка №4 (через 72 часа) → отказ
Ожидаемый результат1. Уведомление менеджеру не отправлялось после первых 3 отказов
2. После 4-го отказа (3-я retry попытка) менеджер получил сообщение в ВК: «У студента [ФИО] 3 отказа по подписке на курс [название]. Свяжитесь со студентом для смены способа оплаты»
Пост-условияПодписка студента переведена в статус payment_failed
ОкружениеТестовая среда PayLect, мок Т-Банка, возвращающий ошибку insufficient_funds

ТК-07. Отображение дашборда с аналитикой по курсам

ПолеЗначение
IDTC-007
НазваниеПросмотр аналитики в личном кабинете PayLect
Связанные требованияSR-09, SYS-24
Предусловия1. PayLect работает 3 месяца
2. Есть данные по 3 курсам школы
3. Владелец школы авторизован в личном кабинете
Шаги1. Владелец открывает личный кабинет PayLect
2. Переходит на вкладку «Аналитика»
3. Выбирает курс «Python для начинающих»
4. Выбирает период «Последние 30 дней»
Ожидаемый результатНа дашборде отображаются метрики:
- Общая выручка за период
- Количество оплат
- LTV (средний чек × количество платежей на студента)
- Отток (доля студентов, прекративших оплату)
Все метрики загружаются < 3 секунд
Пост-условияПри переключении на другой курс метрики пересчитываются корректно
ОкружениеТестовая БД с синтетическими данными за 3 месяца

ТК-08. Идемпотентность платежа

ПолеЗначение
IDTC-008
НазваниеПовторный запрос с одинаковым Idempotency-Key не создаёт дубль
Связанные требованияSYS-01, SYS-02, NFR-02
Предусловия1. PayLect API доступен
2. Сгенерирован уникальный Idempotency-Key = uuid-123
Шаги1. Отправить POST /api/v1/payment с Idempotency-Key: uuid-123 → успех, payment_id = P1
2. Тут же отправить второй такой же запрос с Idempotency-Key: uuid-123
Ожидаемый результат1. Второй запрос вернул HTTP 409 Conflict
2. Тело ответа содержит payment_id = P1 (тот же, что в первом запросе)
3. В БД создан только один платёж (нет дубля)
Пост-условияЧерез 31 день ключ удаляется, новый запрос с тем же ключом создаст платёж
ОкружениеТестовый API PayLect

ТК-09. Задержка уведомления менеджера (производительность)

ПолеЗначение
IDTC-009
НазваниеВремя отправки уведомления менеджеру не превышает 10 секунд
Связанные требованияSYS-15, NFR-05
Предусловия1. Система под нагрузкой 50 RPS
2. Мониторинг времени ответа включён
Шаги1. Студент инициирует оплату (засечь время T0)
2. Провести успешный платёж
3. Засечь время получения уведомления менеджером T1
Ожидаемый результатT1 - T0 ≤ 10 секунд для 95% платежей
Пост-условияВ логах зафиксирована метрика notification_delivery_ms
ОкружениеНагрузочный стенд с k6 или JMeter

ТК-10. Аутентификация по HMAC-SHA256

ПолеЗначение
IDTC-010
НазваниеAPI Gateway отклоняет запросы с неверной подписью
Связанные требованияSYS-21, SYS-22
Предусловия1. Школа зарегистрирована, получены Public Key и Secret Key
2. На сервере школы время синхронизировано с NTP
Шаги1. Сформировать запрос с корректной подписью → ожидаем 200
2. Сформировать запрос с произвольной подписью → ожидаем 401
3. Сформировать запрос с подписью от другой школы → ожидаем 401
4. Сформировать запрос с timestamp = текущее время - 6 минут → ожидаем 401
Ожидаемый результатТолько правильно подписанные запросы с актуальным timestamp проходят аутентификацию
Пост-условияВ логах аудита зафиксированы все отклонённые запросы с причиной
ОкружениеТестовый API, скрипт на Python для генерации подписей

ТК-11. Rate limiting (ограничение частоты запросов)

ПолеЗначение
IDTC-011
НазваниеПревышение лимита 5 запросов в минуту блокирует IP
Связанные требованияSYS-23
Предусловия1. API Gateway доступен
2. Тестовый IP-адрес 192.168.1.100
Шаги1. Отправить 5 запросов POST /api/v1/payment с IP 192.168.1.100 за 50 секунд → все успешны (200)
2. Отправить 6-й запрос с того же IP
Ожидаемый результат6-й запрос вернул HTTP 429 Too Many Requests
Тело ответа: {"error": "rate limit exceeded", "retry_after": 60, "code": 429}
Пост-условияЧерез 60 секунд запрос с того же IP снова принимается
ОкружениеТестовый API, нагрузочный скрипт
