7. Нефункциональные требования (NFR)

7.1. NFR-01: Безопасность

Описание

Система должна обеспечивать защиту платёжных данных, персональной информации пользователей и денежных средств от несанкционированного доступа, перехвата, подмены или утечки.

Реализация

  • Отсутствие данных карт: Платёжная страница банка (редирект) — данные карты не проходят через сервер PayLect
  • Шифрование каналов: Все API-эндпоинты только через HTTPS (TLS 1.2+), HSTS-заголовки
  • Аутентификация: Пара ключей для каждой школы: Public Key (идентификатор) и Secret Key (подпись)
  • Подпись запросов: Все вебхуки и API-запросы подписываются HMAC-SHA256 с использованием Secret Key
  • Защита от подмены: Проверка временной метки (timestamp) в подписанных запросах — отклонение запросов старше 5 минут
  • Rate limiting: Ограничение количества запросов с одного IP (5 запросов/минуту)
  • Ролевая модель: В личном кабинете PayLect: владелец школы, бухгалтер, тех. администратор, менеджер

7.2. NFR-02: Идемпотентность

Описание

Повторное выполнение одного и того же запроса должно давать тот же результат, что и однократное выполнение. Система должна гарантировать, что случайные дублирующиеся запросы не приводят к повторным списаниям средств.

Реализация

  • Idempotency-Key: При создании платежа клиент передаёт заголовок Idempotency-Key: <уникальный_ключ>
  • Хранение ключей: Таблица idempotency_keys с полями: key, payment_id, created_at, expires_at
  • Алгоритм проверки: Если ключ существует — возвращаем ранее созданный платёж, не создавая новый
  • Срок жизни ключа: 30 дней (стандарт для платёжных систем)
  • Защита на уровне БД: Уникальное ограничение (UNIQUE) на поле order_id в таблице платежей

Метрики и критерии проверки

МетрикаЦелевое значениеМетод проверки
Повторные запросы с одинаковым ключомНе создают дублей (0%)Тест-кейс: 3 запроса → 1 платёж
Дублирование по order_idНевозможно (UNIQUE constraint)Тест-кейс: вставка дубля → ошибка
Срок жизни ключа30 днейИнспекция кода + тест TTL

7.3. NFR-03: Отказоустойчивость

Описание

Система сохраняет работоспособность или корректно восстанавливается при сбоях отдельных компонентов — недоступности базы данных, банка, сети, собственных серверов.

Реализация

  • База данных: Репликация — PostgreSQL с автоматическим переключением
  • API-серверы: Горизонтальное масштабирование — минимум 2 экземпляра за балансировщиком (Nginx / HAProxy)
  • Запросы к банку: Таймауты и ретраи — таймаут 30 сек, повтор через 1, 2, 4 сек при ошибках 5xx
  • Вебхуки к школе: Очередь с подтверждением — RabbitMQ, повтор через 1, 5, 15, 60 минут
  • Graceful shutdown: Корректное завершение — SIGTERM → не принимать новые запросы, завершить текущие (макс 30 сек)

Метрики и критерии проверки

МетрикаЦелевое значениеМетод проверки
Доступность99.9% в месяцМониторинг (Prometheus)
RTO (Recovery Time Objective)≤ 15 минутДокументация, тест восстановления
RPO (Recovery Point Objective)≤ 5 минутДокументация, тест потери данных

7.4. NFR-04: Строгий аудит и трассируемость операций

Описание

Каждое действие в системе (особенно связанное с деньгами) должно быть зафиксировано в неизменяемом логе. Должна быть возможность восстановить полную цепочку событий по любой операции.

Что логируется

  • API-запросы: IP, timestamp, endpoint, метод, параметры (кроме данных карты), код ответа
  • Платежи: Каждый статус: created → pending → succeeded / failed / refunded с timestamp
  • Вебхуки: Что отправлено, URL, код ответа школы (или ошибка), количество попыток
  • Действия в личном кабинете: Кто (user_id), действие, timestamp
  • Системные события: Запуск retry, ошибка банка, недоступность CRM

Требования к аудиту

  • Неизменяемость: Логи в формате append-only (только добавление). Запрет UPDATE/DELETE на уровне БД
  • Целостность: Каждая запись лога подписывается хешем от предыдущей (цепочка SHA-256)
  • Хранение: Не менее 3 лет (требование для платёжных систем)
  • Доступность для выгрузки: Школа может скачать лог по своим платежам за период в CSV/JSON
  • Защита от подделки: Хеш-цепочка хранится отдельно; при проверке обнаруживается любое изменение

Метрики и критерии проверки

МетрикаЦелевое значениеМетод проверки
Время построения аудит-отчёта за месяц≤ 5 секундНагрузочный тест
Целостность логовХеш-цепочка сходитсяКриптографическая проверка
Каждый платёж имеет полную историю100% платежейВыборка из БД

7.5. NFR-05: Производительность и пропускная способность

Описание

Система должна обрабатывать заданное количество запросов в единицу времени без деградации качества обслуживания.

Реализация

  • Кэширование часто запрашиваемых данных: Redis для кэширования справочников, сессий, API-ключей
  • Асинхронная обработка: Все длительные операции (вебхуки, уведомления) через очереди (RabbitMQ)
  • Оптимизация запросов: Индексы в PostgreSQL, explain-анализ медленных запросов

7.6. NFR-06: Надёжность и устойчивость к сбоям

Описание

Система должна сохранять целостность данных и корректно обрабатывать ошибки при сбоях внешних систем или внутренних компонентов.

Реализация

  • Health checks: Эндпоинты /health (liveness) и /ready (readiness) для каждого сервиса
  • Graceful degradation: При недоступности второстепенных сервисов (ВК, CRM) — уведомление в лог, продолжение работы
  • Retry с exponential backoff: Для запросов к внешним API (банк, CRM, ВК): 1, 2, 4, 8 секунд
  • Circuit breaker: При 5 последовательных ошибках к внешнему API — временная блокировка на 30 секунд
  • Мониторинг и алерты: Prometheus + Grafana + Alertmanager (алерты в ВК при падении)

Метрики и критерии проверки

Успешность повторных попыток (retry)≥ 95% после 3 попытокАнализ логов за месяц
Время обнаружения сбоя (MTTD)≤ 2 минутМониторинг (Prometheus)
Время восстановления после сбоя (MTTR)≤ 15 минутДокументация, тест восстановления

7.7. NFR-07: Масштабируемость

Описание

Система должна поддерживать рост количества школ, платежей и пользователей без кардинальной смены архитектуры.

Реализация

  • Горизонтальное масштабирование API: Stateless приложение → можно добавлять экземпляры под нагрузкой
  • Шардирование БД: По school_id (одна школа → один шард)
  • Чтение из реплик: Для отчётов и дашбордов — чтение из реплики, запись в мастер
  • Очереди для асинхронных задач: RabbitMQ — несколько воркеров могут обрабатывать очередь

7.8. NFR-08: Совместимость и интеграционная способность

Описание

Система должна корректно взаимодействовать с внешними системами (Т-Банк, Битрикс24, 1С, ВК) при изменениях их API.

Реализация

  • Адаптеры для внешних API: Отдельный слой адаптеров для каждого внешнего сервиса
  • Версионирование API: PayLect API имеет версию в URL: /api/v1/..., /api/v2/...
  • Fallback-форматы: При изменении формата от банка — поддержка старого формата 30 дней
  • Мониторинг изменений: Подписка на changelog внешних систем (email-рассылки, RSS)
  • Тестовые контракты: Pact-тесты для каждого внешнего API

7.9. NFR-09: Юзабилити и удобство интеграции

Описание

Система должна быть простой в подключении для школ без технического бэкграунда.

Реализация

  • Готовые плагины: WordPress-плагин (установка из каталога), шаблон для Tilda
  • Понятный личный кабинет: Интуитивный интерфейс, подсказки, видео-туториалы
  • API-ключи одной кнопкой: Генерация Public/Secret Key в 1 клик
  • Документация для разработчиков: Swagger/OpenAPI, примеры кода на PHP/Python/JS
  • Индикаторы статуса: В личном кабинете — зелёный/красный статус каждой интеграции

7.10. NFR-10: Наблюдаемость

Описание

Система должна предоставлять достаточную информацию для мониторинга, отладки и анализа инцидентов.

Реализация

  • Метрики: RPS, ошибки, задержки, количество активных подписок
  • Логирование: Structured logs (JSON), уровень логирования: INFO, WARN, ERROR
  • Дашборды: Grafana: технические метрики + бизнес-метрики (выручка, отток)
  • Алерты: Alertmanager: алерты в ВК при превышении порогов
