# 10. Реестр рисков

## Риск №1. Отказ банка-эквайера (Т-Банк) при списании

| Поле | Описание |
|------|----------|
| **Причина** | Технический сбой в Т-Банке, DDoS, обрыв связи, плановые работы |
| **Событие** | API Т-Банка возвращает 5xx или таймаут при запросе на списание |
| **Последствие** | Платёж не выполнен, студент не получает доступ, выручка потеряна, менеджер не уведомлён |
| **Вероятность / Ущерб** | Средняя / Высокий (прямая потеря выручки) |
| **Меры** | Таймауты 30 сек, ретраи 1/2/4 сек, очередь RabbitMQ, возврат 503 школе, алерт в мониторинг |
| **Остаточный риск** | Низкий (при длительном отказе >1 часа выручка теряется) |

## Риск №2. Потеря вебхука при недоступности сайта школы

| Поле | Описание |
|------|----------|
| **Причина** | Сайт школы (WordPress/Tilda) временно недоступен, возвращает 5xx или таймаут |
| **Событие** | PayLect не может доставить вебхук об успешном платеже |
| **Последствие** | Сайт не обновляет статус платежа, студент не видит подтверждения, возможен двойной доступ вручную |
| **Вероятность / Ущерб** | Средняя / Средний (операционные накладки) |
| **Меры** | Очередь вебхуков в RabbitMQ с ретраями 1/5/15/60 минут, dead-letter после 4 попыток, лог ошибок |
| **Остаточный риск** | Низкий (при отказе >2 часов менеджер обработает вручную) |

---

## Риск №3. Сбой аутентификации через HMAC из-за рассинхрона времени

| Поле | Описание |
|------|----------|
| **Причина** | Часы на сервере школы или PayLect расходятся >5 минут (NTP не настроен) |
| **Событие** | API Gateway отклоняет запрос как просроченный (timestamp mismatch) |
| **Последствие** | Все платежи от школы блокируются, выручка падает, менеджеры не в курсе причины |
| **Вероятность / Ущерб** | Низкая / Высокий (полная остановка приёма платежей) |
| **Меры** | Мониторинг NTP на всех серверах, допустимый джиттер ±30 сек, алерт при отклонении >3 сек, инструкция для тех. администратора школы по синхронизации времени |
| **Остаточный риск** | Очень низкий |

---

## Риск №4. Утечка Secret Key школы (компрометация API-ключа)

| Поле | Описание |
|------|----------|
| **Причина** | Ключ сохранён в публичном репозитории, передан по открытому каналу, украден у тех. администратора |
| **Событие** | Злоумышленник формирует подписанные запросы от имени школы |
| **Последствие** | Создание фиктивных платежей, списание средств студентов, потеря репутации, финансовые претензии |
| **Вероятность / Ущерб** | Низкая / Критический |
| **Меры** | Генерация ключей только в личном кабинете, отображение ключа один раз, возможность отзыва/ротации, HTTPS только, аудит всех запросов, алерт на необычную активность |
| **Остаточный риск** | Низкий (при ротации каждые 90 дней) |

## Риск №5. Сбой репликации PostgreSQL и потеря аналитических данных

| Поле | Описание |
|------|----------|
| **Причина** | Отказ реплики, разрыв синхронизации, сбой WAL-логов |
| **Событие** | Dashboard API и Analytics Engine читают устаревшие или неполные данные |
| **Последствие** | Владелец школы видит неверную выручку, LTV, отток → ошибочные бизнес-решения |
| **Вероятность / Ущерб** | Средняя / Средний |
| **Меры** | Мониторинг лага реплики (pg_stat_replication), автоматическое переключение на мастер при чтении, алерт при лаге >5 мин, ежечасная сверка контрольных сумм |
| **Остаточный риск** | Низкий (при полной потере реплики данные восстанавливаются из мастера) |

## Риск №6. Переполнение очереди RabbitMQ при пиковой нагрузке

| Поле | Описание |
|------|----------|
| **Причина** | Резкий рост числа платежей (акция, запуск курса) >1000 RPS |
| **Событие** | Очередь растёт, сообщения начинают дропаться или уходят в DLQ |
| **Последствие** | Задержка обработки платежей, уведомлений, вебхуков → студенты не получают доступ вовремя |
| **Вероятность / Ущерб** | Низкая / Средний |
| **Меры** | Автомасштабирование воркеров (K8s HPA по длине очереди), мониторинг очереди, алерт при >10k сообщений, предварительное нагрузочное тестирование |
| **Остаточный риск** | Очень низкий (при превышении лимитов школы платят за приоритетную обработку) |

## Риск №7. Сбой leader election у Retry Scheduler (двойные списания)

| Поле | Описание |
|------|----------|
| **Причина** | Сетевой split-brain, сбой блокировки в PostgreSQL или K8s lease |
| **Событие** | Два экземпляра Retry Scheduler одновременно запускают одно и то же повторное списание |
| **Последствие** | Со студента списывается сумма дважды → chargeback, жалобы, потеря доверия |
| **Вероятность / Ущерб** | Низкая / Высокий |
| **Меры** | Использование PostgreSQL advisory lock с TTL, идемпотентность по payment_id, проверка статуса перед списанием, аудит всех retry-операций |
| **Остаточный риск** | Очень низкий |

---

## Риск №8. Недоступность сервиса уведомлений (ВК / СМС-провайдер)

| Поле | Описание |
|------|----------|
| **Причина** | Блокировка API VK, сбой у СМС-провайдера, квота превышена |
| **Событие** | Notification Dispatcher не может отправить сообщение |
| **Последствие** | Менеджер не узнаёт о покупке → задержка доступа студента → отток. Студент не получает напоминание о списании → неожиданный платёж |
| **Вероятность / Ущерб** | Средняя / Средний |
| **Меры** | Логирование ошибки, fallback на альтернативный канал (Telegram или email), ретраи с exponential backoff, алерт инженерам, дублирование в личном кабинете (список "неудачных уведомлений") |
| **Остаточный риск** | Низкий (менеджер может зайти в личный кабинет и увидеть новые платежи вручную) |

## Риск №9. Ошибка в интеграции с 1С (дублирование документов)

| Поле | Описание |
|------|----------|
| **Причина** | Повторный запуск внешней обработки без проверки last_sync_id, сбой идемпотентности |
| **Событие** | Один и тот же платёж выгружается в 1С несколько раз |
| **Последствие** | Бухгалтер видит задвоенные поступления, не сходится с выпиской банка, ошибки в отчётности |
| **Вероятность / Ущерб** | Средняя / Средний |
| **Меры** | Эндпоинт GET /api/v1/payments поддерживает параметр last_sync_id, обработка хранит последний успешный ID, проверка "уже проведён" в 1С, ручная сверка раз в месяц |
| **Остаточный риск** | Низкий (при обучении бухгалтера) |

---

## Риск №10. Падение Redis с потерей горячих метрик

| Поле | Описание |
|------|----------|
| **Причина** | Сбой сервера Redis, не включена persistence (RDB/AOF) |
| **Событие** | Все горячие метрики (выручка за сегодня/неделю, LTV) потеряны |
| **Последствие** | Дашборд временно пуст, владелец не видит актуальную аналитику |
| **Вероятность / Ущерб** | Низкая / Низкий |
| **Меры** | Включена AOF с fsync everysec, автоматический перезапуск Redis, снимки RDB каждые 6 часов, восстановление метрик из агрегатных таблиц PostgreSQL при старте |
| **Остаточный риск** | Очень низкий (простой дашборда до 5 минут) |
