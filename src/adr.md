### 8.2. ADR

### ADR-01: Отказ от хранения данных карты → редирект на банк

| Поле | Значение |
|------|----------|
| **Статус** | Принято |
| **Дата** | 2026-05-06 |
| **Автор** | Архитектор PayLect |

**Контекст**

Система принимает платежи, но требования безопасности (SR-10, NFR-01) запрещают хранение данных карт (PAN, CVV, срок действия). Необходимо выбрать способ приёма платежей, исключающий попадание платёжных данных в PayLect.

**Решение**

Перенаправлять пользователя на платёжную страницу Т-Банка. PayLect получает только токен и статус платежа через вебхук. Данные карты не проходят через сервер PayLect.

**Альтернативы**

| Альтернатива | Почему не выбрана |
|--------------|-------------------|
| iframe с платёжной формой банка | Технически сложнее, риск перехвата данных через JavaScript |
| Собственная форма оплаты с передачей карт через API банка | Требует PCI DSS Level 1 (дорого и сложно) |

**Trade-off обоснование**

| Что выиграли | Чем пожертвовали |
|--------------|------------------|
| Отсутствие PCI DSS Level 1 — снижение стоимости и ответственности | Нельзя кастомизировать платёжную форму под бренд школы |
| Безопасность из коробки (данные карт не попадают в систему) | Зависимость от доступности Т-Банка (частично решается retry и health checks) |
| Упрощение сертификации и аудита | Сложность отладки (редирект на внешний сайт) |

**Последствия**

- Все API-запросы к банку идут через редирект
- Нужно поддерживать вебхуки от Т-Банка для обновления статусов
- PayLect не отвечает за безопасность платёжной формы

### ADR-02: Идемпотентность через Idempotency-Key + UNIQUE(order_id)

| Поле | Значение |
|------|----------|
| **Статус** | Принято |
| **Дата** | 2026-05-06 |
| **Автор** | Архитектор PayLect |

**Контекст**

Повторные запросы от школ (например, студент дважды нажал «Оплатить» или сетевой таймаут вызвал ретрай) не должны создавать дублирующиеся платежи. Необходим механизм идемпотентности (SYS-01, SYS-02, NFR-02).

**Решение**

Клиент передаёт заголовок `Idempotency-Key: <уникальный_ключ>`. Если ключ уже существует в пределах школы — возвращается HTTP 409 Conflict и ранее созданный объект платежа. Ключи хранятся 30 дней. Дополнительная защита — UNIQUE constraint на поле `order_id` в таблице платежей.

**Альтернативы**

| Альтернатива | Почему не выбрана |
|--------------|-------------------|
| Двухфазный коммит | Избыточно для данного масштаба, сложно реализовать |
| Distributed lock (Redis) | Добавляет зависимость от Redis при каждом платеже |
| Проверка по параметрам платежа (сумма+курс+студент) | Ненадёжно — студент может оплатить один курс дважды легально |

**Trade-off обоснование**

| Что выиграли | Чем пожертвовали |
|--------------|------------------|
| Простота реализации (не нужен distributed lock) | Не гарантирует глобальную уникальность между школами (не требуется — ключи изолированы по `school_id`) |
| Высокая производительность (одна проверка в БД) | При сбое БД до сохранения ключа — теоретический риск дубля (крайне редкий сценарий) |
| 30 дней хранения — стандарт платёжных систем | Дополнительная таблица для хранения ключей |

**Последствия**

- Каждый запрос на создание платежа должен содержать `Idempotency-Key`
- API Gateway проверяет ключ до вызова Payment Core
- Периодическая очистка ключей старше 30 дней

### ADR-03: Асинхронная обработка уведомлений и CRM-вебхуков через очередь

| Поле | Значение |
|------|----------|
| **Статус** | Принято |
| **Дата** | 2026-05-06 |
| **Автор** | Архитектор PayLect |

**Контекст**

При успешном платеже нужно: отправить уведомление менеджеру в ВК (SR-01), создать сделку в Битрикс24 (SR-05), обновить аналитику. Если делать синхронно — платёж будет ждать ответа от внешних систем (до таймаута), что замедлит пользователя.

**Решение**

Платёжный оркестратор (Payment Core) публикует событие в RabbitMQ. Отдельные воркеры (Notification Dispatcher, Analytics Engine, CRM-адаптер) забирают сообщения из очереди и обрабатывают их асинхронно. При недоступности внешнего сервиса сообщение остаётся в очереди и повторяется позже (SYS-18).

**Альтернативы**

| Альтернатива | Почему не выбрана |
|--------------|-------------------|
| Синхронные вызовы в коде Payment Core | Тормозят платёжный процесс, нет отказоустойчивости |
| Webhooks от платежного шлюза напрямую | Не интегрируется с системой, нужен публичный endpoint |
| Отдельный микросервис, вызываемый синхронно | Не решает проблему отказоустойчивости |

**Trade-off обоснование**

| Что выиграли | Чем пожертвовали |
|--------------|------------------|
| Платёж подтверждается мгновенно (не зависит от ВК/Битрикс24) | Усложнение архитектуры (очередь + мониторинг + dead-letter) |
| Естественные retry и dead-letter при сбоях внешних сервисов | Возможна задержка уведомления на секунды-минуты (не критично для сценария) |
| Отказоустойчивость: падение ВК не блокирует платежи | — |

**Последствия**

- В RabbitMQ созданы очереди: `notify`, `crm`, `analytics`
- Настроена политика at-least-once доставки
- Dead-letter очередь для необработанных сообщений
- Мониторинг глубины очередей (Prometheus + Grafana)

### ADR-04: Выделенный Retry Scheduler с leader election для повторных списаний

| Поле | Значение |
|------|----------|
| **Статус** | Принято |
| **Дата** | 2026-05-06 |
| **Автор** | Архитектор PayLect |

**Контекст**

При отказе карты нужно автоматически повторять списания (интервалы: 1ч, 24ч, 72ч, настраиваются через School Cabinet, SYS-10, SYS-13). Нужно гарантировать, что retry не дублируются при нескольких экземплярах сервиса.

**Решение**

Выделенный сервис (Retry Scheduler), который в один момент времени активен только один экземпляр (leader election через PostgreSQL advisory lock или K8s lease). Сервис сканирует таблицу `scheduled_jobs`, отправляет команды в Payment Core и обновляет статусы. При успешном списании следующие попытки отменяются (SYS-11).

**Альтернативы**

| Альтернатива | Почему не выбрана |
|--------------|-------------------|
| Встроенный cron в Payment Core | Смешивает ответственности, сложно отключать retry |
| Каждый экземпляр API запускает свой таймер | Гарантированные дубли при нескольких подах в K8s |
| Внешний cron (например, на линуксе) | Не интегрируется с отказоустойчивостью, нет автоматического переключения |

**Trade-off обоснование**

| Что выиграли | Чем пожертвовали |
|--------------|------------------|
| Контроль над дублированием списаний (нет гонок между экземплярами) | Дополнительный компонент, который нужно мониторить |
| Можно перезапускать без влияния на API | Сложнее в K8s (нужен механизм лидерства) |
| Гибкая настройка retry (0–5 попыток, свои интервалы) | При падении единственного инстанса retry останавливаются до восстановления |

**Последствия**

- Таблица `scheduled_jobs` для хранения запланированных retry
- Механизм leader election обязателен (простой флаг в БД или K8s lease)
- При перезапуске сервис восстанавливает расписание из БД
- Отдельный эндпоинт `/health` для проверки лидерства

### ADR-05: Разделение аналитики на Analytics Engine (write) и Dashboard API (read)

| Поле | Значение |
|------|----------|
| **Статус** | Принято |
| **Дата** | 2026-05-06 |
| **Автор** | Архитектор PayLect |

**Контекст**

Нужно показывать дашборды с выручкой, LTV, оттоком (SR-09, SYS-24). Запросы к сырым данным платежей требуют тяжёлых агрегаций (секунды). Но данные должны быть свежими (секунды после платежа).

**Решение**

CQRS-подход для аналитики: **Analytics Engine** (write) слушает очередь, обновляет горячие метрики в Redis (today/week/month) и агрегатные таблицы в PostgreSQL (course_daily_revenue, ltv_by_student, churn_monthly). **Dashboard API** (read) читает готовые метрики из Redis (горячие за <1 мс) и из агрегатных таблиц PostgreSQL (исторические за 10–50 мс). School Cabinet обращается только к Dashboard API.

**Альтернативы**

| Альтернатива | Почему не выбрана |
|--------------|-------------------|
| Прямые запросы из School Cabinet к сырым таблицам | Медленно (секунды), убивает БД при нагрузке |
| Единый сервис, который и пишет, и читает | Сложно масштабировать отдельно (читателей нужно больше) |
| Только PostgreSQL без агрегатных таблиц | Тяжёлые GROUP BY на сотнях миллионов записей |
| ClickHouse для аналитики | Избыточно для 10 000 школ и 1 млн платежей/день |

**Trade-off обоснование**

| Что выиграли | Чем пожертвовали |
|--------------|------------------|
| Дашборды работают за <1 мс (горячие) и <50 мс (исторические) | Нужно поддерживать две сущности: Analytics Engine и Dashboard API |
| Аналитика не тормозит платёжный процесс (асинхронное обновление) | Исторические отчёты (за год) могут отставать на час (если агрегаты считаются раз в час) |
| PostgreSQL не страдает от тяжёлых запросов дашбордов (все данные предрассчитаны) | — |
| Redis кэширует горячие метрики, разгружая PostgreSQL | Redis нужно настраивать persistence (RDB/AOF) |

**Последствия**

- Analytics Engine слушает очередь `analytics` в RabbitMQ
- Dashboard API развёрнут как отдельный HTTP-сервис
- Агрегатные таблицы обновляются инкрементально при каждом платеже
- LTV/отток пересчитываются раз в час фоном
- При отказе Analytics Engine дашборды показывают старые данные из Redis/PostgreSQL
