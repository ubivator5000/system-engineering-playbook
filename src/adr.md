## 8.2. ADR

## ADR-001: Использование событийно-ориентированной архитектуры (Event-Driven) с очередью сообщений

## Статус
**Принято**

## Контекст
PayLect должен обрабатывать платежи, уведомления, вебхуки и аналитику. При пиковых нагрузках (запуск курса, акция) прямые синхронные вызовы могут привести к таймаутам, потере данных и недоступности API. Также требуется гарантированная доставка вебхуков при временной недоступности внешних систем (сайт школы, CRM, 1С).

## Решение
Использовать **событийно-ориентированную архитектуру** с **RabbitMQ** в качестве основной очереди сообщений. Все критически важные операции (создание платежа, обновление статуса, отправка уведомлений, вебхуки) проходят через очередь. Поток:

1. API Gateway принимает запрос, проверяет идемпотентность и публикует событие `payment.created`.
2. Payment Core (воркер) забирает событие, вызывает Т-Банк, публикует `payment.succeeded` / `payment.failed`.
3. Notification Dispatcher и другие потребители реагируют на события.

## Последствия (Trade-offs)

| ✅ Плюсы | ❌ Минусы |
|----------|----------|
| Асинхронность → развязка сервисов, отказоустойчивость | Усложнение отладки (трассировка через очередь) |
| Гарантированная доставка (persistent queues, retries) | Дополнительная инфраструктура (RabbitMQ/Kafka) |
| Автомасштабирование воркеров по длине очереди | Возможна задержка обработки (milliseconds → seconds) |
| Нет потери данных при падении потребителей | Лишний overhead для простых операций (например, health check) |

## Альтернативы
- **Синхронная архитектура (REST только)** — проще, но не гарантирует доставку вебхуков, падает при всплесках.
- **Kafka вместо RabbitMQ** — больше пропускная способность, но сложнее в эксплуатации. Для текущих 100 RPS RabbitMQ достаточно.

## Решение оставлено в силе, потому что:
Надёжность доставки вебхуков и восстановление после сбоев важнее небольшого усложнения инфраструктуры.

## ADR-002: Идемпотентность через Idempotency-Key (заголовок + БД)

## Статус
**Принято**

## Контекст
При создании платежа школа может случайно отправить два одинаковых запроса (сетевой ретрай, дубль от виджета, баг). Повторное списание — недопустимо. PayLect должен гарантировать, что каждый платёж создаётся ровно один раз.

## Решение
Внедрить **Idempotency-Key** механизм:

- Клиент передаёт заголовок `Idempotency-Key: <UUID>` при POST `/api/v1/payments`.
- Система проверяет наличие ключа в таблице `idempotency_keys`.
- Если ключ существует → возвращаем ранее созданный платёж (HTTP 200 или 409).
- Если ключа нет → создаём платёж, сохраняем ключ со ссылкой на `payment_id`.
- TTL ключа — **30 дней** (стандарт Stripe).

Дополнительно: UNIQUE constraint на `order_id` в пределах одной школы (на случай, если школа не передаёт Idempotency-Key).

## Последствия (Trade-offs)

| ✅ Плюсы | ❌ Минусы |
|----------|----------|
| Полная защита от дублей платежей | Дополнительное хранилище (таблица + индексы) |
| Прозрачно для школы (просто передать UUID) | Рост таблицы → нужна очистка старых ключей |
| Повторный запрос возвращает тот же результат (идемпотентность) | 30 дней хранения → ~1 млн ключей на 100k платежей/мес |

## Альтернативы
- **Только UNIQUE на order_id** — дешевле, но требует, чтобы школа сама гарантировала уникальность. Не защищает от повторного запроса с тем же `order_id`.
- **Использование Redis только для Idempotency** — быстрее, но ключи потеряются при рестарте. БД + Redis в тандеме сложнее.

## Решение оставлено в силе, потому что:
Платежи — критическая доменная логика. Лучше переплатить за хранение и индекс, чем допустить двойное списание.

## ADR-003: CQRS для разделения команд (платежи) и запросов (аналитика)

## Статус
**Принято**

## Контекст
Владельцы школ требуют богатую аналитику (выручка по курсам, LTV, отток, MRR). Одновременно платёжный процесс требует высокой доступности и предсказуемой задержки (<500 мс). Смешивание тяжёлых аналитических запросов с транзакционными записями в одной БД приводит к деградации производительности платежей. Прямые SQL-запросы на миллионах платежей становятся слишком медленными.

## Решение
Применить **CQRS (Command Query Responsibility Segregation)** без полного Event Sourcing (медиаторный CQRS):

### Command side (запись)
- **PostgreSQL (мастер)** — нормализованная схема.
- Только `INSERT/UPDATE` через Payment Core.
- Минимум индексов, только для уникальности и внешних ключей.

### Query side (чтение)
- **Redis** — горячие метрики (сегодня, неделя, месяц) с TTL.
- **PostgreSQL (реплика, агрегатные таблицы)** — `course_daily_revenue`, `ltv_by_student`, `churn_monthly`.
- **Analytics Engine** (фоновый сервис) слушает очередь событий и обновляет агрегаты асинхронно.
- **Dashboard API** — читает из Redis (hot path) и из агрегатных таблиц (cold path).

## Последствия (Trade-offs)

| ✅ Плюсы | ❌ Минусы |
|----------|----------|
| Аналитика не тормозит приём платежей | Асинхронность → аналитика может отставать на 1–5 секунд (eventual consistency) |
| Можно масштабировать query-реплики отдельно | Дополнительная инфраструктура (Redis, агрегатные таблицы, воркер) |
| Горячие метрики из Redis за <1 мс | Усложнение логики (два способа хранения) |
| Естественное разделение ответственности сервисов | Риск рассинхрона между мастером и агрегатами |

## Альтернативы
- **Обычная монолитная БД с индексами** — просто, но при 1M+ платежей аналитика падает до минут.
- **Полный Event Sourcing (все события хранятся, снапшоты)** — абсолютная трассируемость, но колоссальное усложнение, не нужно на старте.
- **OLAP-хранилище (ClickHouse)** — мощно, но перебор для 10k школ. PostgreSQL агрегатов достаточно.

## Решение оставлено в силе, потому что:
Для целевых 10 000 школ и 1 млн платежей в день CQRS с агрегатными таблицами даёт оптимальный баланс между сложностью и производительностью.
