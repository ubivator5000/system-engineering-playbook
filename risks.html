10. Реестр рисков

Риск №1. Отказ банка-эквайера (Т-Банк) при списании

ПолеОписание
ПричинаТехнический сбой в Т-Банке, DDoS, обрыв связи, плановые работы
СобытиеAPI Т-Банка возвращает 5xx или таймаут при запросе на списание
ПоследствиеПлатёж не выполнен, студент не получает доступ, выручка потеряна, менеджер не уведомлён
Вероятность / УщербСредняя / Высокий (прямая потеря выручки)
МерыТаймауты 30 сек, ретраи 1/2/4 сек, очередь RabbitMQ, возврат 503 школе, алерт в мониторинг
Остаточный рискНизкий (при длительном отказе >1 часа выручка теряется)

Риск №2. Потеря вебхука при недоступности сайта школы

ПолеОписание
ПричинаСайт школы (WordPress/Tilda) временно недоступен, возвращает 5xx или таймаут
СобытиеPayLect не может доставить вебхук об успешном платеже
ПоследствиеСайт не обновляет статус платежа, студент не видит подтверждения, возможен двойной доступ вручную
Вероятность / УщербСредняя / Средний (операционные накладки)
МерыОчередь вебхуков в RabbitMQ с ретраями 1/5/15/60 минут, dead-letter после 4 попыток, лог ошибок
Остаточный рискНизкий (при отказе >2 часов менеджер обработает вручную)

Риск №3. Сбой аутентификации через HMAC из-за рассинхрона времени

ПолеОписание
ПричинаЧасы на сервере школы или PayLect расходятся >5 минут (NTP не настроен)
СобытиеAPI Gateway отклоняет запрос как просроченный (timestamp mismatch)
ПоследствиеВсе платежи от школы блокируются, выручка падает, менеджеры не в курсе причины
Вероятность / УщербНизкая / Высокий (полная остановка приёма платежей)
МерыМониторинг NTP на всех серверах, допустимый джиттер ±30 сек, алерт при отклонении >3 сек, инструкция для тех. администратора школы по синхронизации времени
Остаточный рискОчень низкий

Риск №4. Утечка Secret Key школы (компрометация API-ключа)

ПолеОписание
ПричинаКлюч сохранён в публичном репозитории, передан по открытому каналу, украден у тех. администратора
СобытиеЗлоумышленник формирует подписанные запросы от имени школы
ПоследствиеСоздание фиктивных платежей, списание средств студентов, потеря репутации, финансовые претензии
Вероятность / УщербНизкая / Критический
МерыГенерация ключей только в личном кабинете, отображение ключа один раз, возможность отзыва/ротации, HTTPS только, аудит всех запросов, алерт на необычную активность
Остаточный рискНизкий (при ротации каждые 90 дней)

Риск №5. Сбой репликации PostgreSQL и потеря аналитических данных

ПолеОписание
ПричинаОтказ реплики, разрыв синхронизации, сбой WAL-логов
СобытиеDashboard API и Analytics Engine читают устаревшие или неполные данные
ПоследствиеВладелец школы видит неверную выручку, LTV, отток → ошибочные бизнес-решения
Вероятность / УщербСредняя / Средний
МерыМониторинг лага реплики (pg_stat_replication), автоматическое переключение на мастер при чтении, алерт при лаге >5 мин, ежечасная сверка контрольных сумм
Остаточный рискНизкий (при полной потере реплики данные восстанавливаются из мастера)

Риск №6. Переполнение очереди RabbitMQ при пиковой нагрузке

ПолеОписание
ПричинаРезкий рост числа платежей (акция, запуск курса) >1000 RPS
СобытиеОчередь растёт, сообщения начинают дропаться или уходят в DLQ
ПоследствиеЗадержка обработки платежей, уведомлений, вебхуков → студенты не получают доступ вовремя
Вероятность / УщербНизкая / Средний
МерыАвтомасштабирование воркеров (K8s HPA по длине очереди), мониторинг очереди, алерт при >10k сообщений, предварительное нагрузочное тестирование
Остаточный рискОчень низкий (при превышении лимитов школы платят за приоритетную обработку)

Риск №7. Сбой leader election у Retry Scheduler (двойные списания)

ПолеОписание
ПричинаСетевой split-brain, сбой блокировки в PostgreSQL или K8s lease
СобытиеДва экземпляра Retry Scheduler одновременно запускают одно и то же повторное списание
ПоследствиеСо студента списывается сумма дважды → chargeback, жалобы, потеря доверия
Вероятность / УщербНизкая / Высокий
МерыИспользование PostgreSQL advisory lock с TTL, идемпотентность по payment_id, проверка статуса перед списанием, аудит всех retry-операций
Остаточный рискОчень низкий

Риск №8. Недоступность сервиса уведомлений (ВК / СМС-провайдер)

ПолеОписание
ПричинаБлокировка API VK, сбой у СМС-провайдера, квота превышена
СобытиеNotification Dispatcher не может отправить сообщение
ПоследствиеМенеджер не узнаёт о покупке → задержка доступа студента → отток. Студент не получает напоминание о списании → неожиданный платёж
Вероятность / УщербСредняя / Средний
МерыЛогирование ошибки, fallback на альтернативный канал (Telegram или email), ретраи с exponential backoff, алерт инженерам, дублирование в личном кабинете (список "неудачных уведомлений")
Остаточный рискНизкий (менеджер может зайти в личный кабинет и увидеть новые платежи вручную)

Риск №9. Ошибка в интеграции с 1С (дублирование документов)

ПолеОписание
ПричинаПовторный запуск внешней обработки без проверки last_sync_id, сбой идемпотентности
СобытиеОдин и тот же платёж выгружается в 1С несколько раз
ПоследствиеБухгалтер видит задвоенные поступления, не сходится с выпиской банка, ошибки в отчётности
Вероятность / УщербСредняя / Средний
МерыЭндпоинт GET /api/v1/payments поддерживает параметр last_sync_id, обработка хранит последний успешный ID, проверка "уже проведён" в 1С, ручная сверка раз в месяц
Остаточный рискНизкий (при обучении бухгалтера)

Риск №10. Падение Redis с потерей горячих метрик

ПолеОписание
ПричинаСбой сервера Redis, не включена persistence (RDB/AOF)
СобытиеВсе горячие метрики (выручка за сегодня/неделю, LTV) потеряны
ПоследствиеДашборд временно пуст, владелец не видит актуальную аналитику
Вероятность / УщербНизкая / Низкий
МерыВключена AOF с fsync everysec, автоматический перезапуск Redis, снимки RDB каждые 6 часов, восстановление метрик из агрегатных таблиц PostgreSQL при старте
Остаточный рискОчень низкий (простой дашборда до 5 минут)
